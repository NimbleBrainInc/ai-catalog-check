# ai-catalog-check

A conformance suite for the AI Catalog spec, run as a CLI or a GitHub Action. The
README says what it does for a user; this file is for changing it.

## How it fits together

| Path | What |
|---|---|
| `spec/<version>/` | Each spec version's Markdown and example file, vendored at the commit its registry names. Never edited. |
| `requirements/<version>.yaml` | Each version's registry: every normative statement, numbered, with its disposition. The files here are the versions the suite checks. |
| `src/extract.ts` | Spec Markdown → its normative statements and CDDL rules |
| `src/spec-facts.ts` | What checks need beyond the sentences, read from the spec: CDDL members and types, known media types, protected `typ` values |
| `src/sync.ts` | Spec ↔ registry diff (`npm run sync`), also the traceability test |
| `src/checks/*.ts` | One function per checked requirement, keyed by its ID |
| `src/discover.ts` | Website URL → its catalog, by the spec's discovery order |
| `src/run.ts` | Files the checks by mode, runs them, maps findings to statuses, computes the level, applies a baseline |
| `src/report.ts`, `src/cli.ts`, `action.yml` | Text, JSON and GitHub output; the CLI; the composite action |
| `test/cases.ts` | `complete.json` and one way to break each checked requirement |
| `scripts/build-sdk.ts` | Builds Vercel's SDK at a pinned commit for `test/sdk-oracle.test.ts` |
| `COVERAGE.md` | Generated by `npm run coverage`; a test fails when it is stale |
| `skills/ai-catalog-check/` | The Agent Skill that teaches an agent to use the CLI; `test/skill.test.ts` holds it to the CLI |

## Rules

- **The registry is the spec, numbered.** An entry's `text` is the spec's sentence
  word for word. The traceability test fails on a statement with no entry, an entry
  whose text is not in the spec, or a checked entry with no check. Do not paraphrase.
- **A catalog is checked against the version it declares.** `run` picks the version
  from the catalog's `specVersion` (or `--spec`), loads that version's registry and
  spec facts, and runs the checks that registry lists. A well-formed version the suite
  does not check is answered, not checked.
- **An ID keeps one meaning in every version.** When a new spec version changes what a
  statement requires, the statement gets a new ID in the new registry and the old ID is
  retired there. A check therefore never asks which version it runs under; it reads
  version-specific facts from `ctx.facts`.
- **Read facts from the spec; do not restate them.** A table a check needs (members,
  types, media types, header values) comes from `spec-facts.ts`, which reads the spec
  and throws when it meets something it cannot read. Code names only what it acts on
  (`MEDIA_TYPES`), and a test holds each name to the spec.
- **A check is filed under its mode.** `CHECKS.document` or `CHECKS.fetch`, as the
  registry's `check:` says; the runner looks it up under that mode only, so a fetch
  check never runs without `--fetch`.
- **The level is the document's.** It counts only document checks, so it does not
  change with `--fetch`; fetch failures still fail the run.
- **IDs are permanent.** Findings, baselines and other repos cite them. A new spec
  version keeps every ID whose statement survives, gives a new statement the next
  free number in its section, and retires a removed one; never renumber.
- **Every entry has exactly one disposition.** `check`, `pending` with a `reason`, or
  `excluded` with a reason. "Restates X" is a reason; so is "binds consumers".
- **Every checked requirement has a `title`**: a few words naming what it asks
  ("Host has a displayName"), shown in every report. A test fails on a checked
  requirement without one.
- **A requirement's strength sets its status.** MUST fails, SHOULD warns. A check does
  not choose; the one exception is a notice (`notice: true` on a violation), for
  advice the spec hedges with "when applicable".
- **Each checked requirement has a case in `test/cases.ts`** (or `test/fetch.test.ts`
  for fetch checks) that breaks it. A test fails when one is missing.
- **Whatever the SDK rejects, a MUST must fail.** `test/sdk-oracle.test.ts` runs the SDK
  over the corpus. When it finds a gap, the fix is a check for the spec statement the
  SDK enforces, not an exception.
- **A spec example a MUST rejects is a spec bug** when the check is right. Record it in
  `KNOWN_SPEC_ERRORS` (`test/spec-examples.ts`) with what the spec gets wrong, and
  report it upstream.
- **The skill changes with the CLI.** A change to flags, output or the fix for a common
  finding updates `skills/ai-catalog-check/SKILL.md` in the same commit. Its starter
  catalog must conform, and every ID it names must exist; a test checks both.
- **The suite checks the spec and nothing else.** A pass means the catalog conforms to
  the AI Catalog spec. A publisher's own conventions belong where its catalog is
  generated, not here; a publisher that wants SHOULDs enforced runs `--strict`.

## Adding a spec version

A new version is added beside the others; existing versions keep working.

1. Vendor its `specification/ai-catalog.md` and `specification/examples/` as
   `spec/<version>/`, and copy the newest registry to `requirements/<version>.yaml`
   with the new `spec:` version, commit, tag and published URL.
2. `node src/sync.ts spec/<version>/ai-catalog.md <version>` lists the statements the
   new spec adds (`+`), drops (`-`) and moves (`~`). Give each added statement the next
   free number in its section; delete dropped ones from the new registry; give a
   statement whose meaning changed a new ID and delete the old one from the new registry.
3. Write a check, and a case in `test/cases.ts`, for each new ID that is checked.
4. Point `SDK_COMMIT` and `SDK_SPEC` in `scripts/build-sdk.ts` at the SDK release for
   the new version.
5. `npm run coverage`, `npm run check`. Adding a version is a minor release; dropping
   one is a major release.

## Commands

```sh
npm ci
npm run check                 # typecheck and tests
node scripts/build-sdk.ts     # once, to run the SDK cross-check locally
npm run coverage              # regenerate COVERAGE.md
npm run sync                  # spec ↔ registry diff
node src/cli.ts <catalog>     # run from source (Node 24 strips the types)
```

## Releases

Consumers pin a tag (`@v0.1.0`). Tag `main` after a merge that changes what the suite
reports, and bump `version` in `package.json` with it. The version describes the tool,
not the spec: a new failing check or a new spec version is a minor release (either can
fail a catalog that passed), and dropping a spec version or a breaking change to the
CLI, the JSON report or the action is a major one.
